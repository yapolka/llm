# LLM Pipeline — учебный мини-продукт

Пайплайн для интеллектуальной обработки текста: принимает произвольный
текст (например, обращение клиента), определяет его категорию, анализирует
тональность и срочность, генерирует ответ в стиле, подходящем для этой
категории, и проверяет собственный результат на противоречия.

Проект сделан по шагам за 7 дней: от одного запроса к модели до
устойчивого многошагового пайплайна с валидацией, retry и самопроверкой.

## Возможности

- Классификация текста по 5 категориям: `support`, `feedback`, `complaint`, `sales`, `general_question`
- Routing: разный стиль ответа в зависимости от категории (явный словарь `ROUTING_INSTRUCTIONS` в коде, а не один огромный промпт)
- 5-шаговый пайплайн: извлечение сути → классификация → структурные поля → генерация ответа → самопроверка
- Валидация каждого шага через Pydantic-схемы
- Retry и fallback при сбоях модели: пустой ответ, невалидный JSON, ошибка схемы (в повторный промпт подставляется текст ошибки валидации)
- Ограничение длины финального ответа (`max_length=800`)
- Устойчивость к ошибкам API (rate limit, неверный ключ, недоступность провайдера): пайплайн возвращает понятную ошибку вместо падения
- Работает с любым OpenAI-совместимым провайдером (OpenAI, Groq, OpenRouter, Ollama и др.)

## Установка

```bash
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env
```

Впиши в `.env` данные своего провайдера. Пример для **Groq** (бесплатный тариф):

```
OPENAI_API_KEY=gsk_твой_ключ
OPENAI_BASE_URL=https://api.groq.com/openai/v1
OPENAI_MODEL=qwen/qwen3.8-27b

# необязательно:
MAX_TOKENS=700
MIN_REQUEST_INTERVAL=3
```

Пример для **OpenAI**:

```
OPENAI_API_KEY=sk-...
OPENAI_MODEL=gpt-4o-mini
```

(для OpenAI `OPENAI_BASE_URL` указывать не нужно)

Имена переменных начинаются с `OPENAI_` для любого провайдера, потому что
используется официальный OpenAI SDK с подменой `base_url`.

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `OPENAI_API_KEY` | ключ API провайдера | обязательна |
| `OPENAI_BASE_URL` | адрес API провайдера | адрес OpenAI |
| `OPENAI_MODEL` | название модели | `gpt-4o-mini` |
| `MAX_TOKENS` | максимум токенов в ответе модели | `700` |
| `MIN_REQUEST_INTERVAL` | минимальная пауза между запросами, секунды | `3` |

## Запуск

Полный пайплайн (5 шагов, 10 тестовых текстов):

```bash
python main.py
```

Результаты выводятся в консоль и сохраняются в `output/day5_results.json`.
Прогон занимает несколько минут: между запросами есть пауза, чтобы
не упираться в лимиты бесплатного тарифа.

Пайплайн только Дня 4 (классификация + routing, 2 шага) отдельным файлом:

```bash
python day4_run.py
```

Результаты сохраняются в `output/day4_results.json`.

## Как это работает

```
текст → [1] extract_meaning → [2] classify_request → [3] build_structured_fields
      → [4] generate_final_answer (routing по категории) → [5] self_check → результат
```

1. **extract_meaning** — выделяет суть текста.
2. **classify_request** — определяет категорию (одна из 5) и намерение.
3. **build_structured_fields** — sentiment (`positive` / `negative` / `neutral`) и urgency.
4. **generate_final_answer** — генерирует ответ; инструкция по стилю берётся из `ROUTING_INSTRUCTIONS` по категории из шага 2.
5. **self_check** — модель проверяет ответ на противоречия с исходным текстом и возвращает `consistent`, `issues`, `verdict` (`ok` / `needs_review`).

Каждый шаг проходит через `_call_step`: вызов модели → разбор JSON →
валидация Pydantic-схемой. При сбое шаг повторяется до 3 раз.

## Пример входа/выхода

Реальные результаты прогона (`output/day5_results.json`).

**Вход:** «Приложение вылетает каждый раз, когда я пытаюсь открыть раздел 'Профиль'. Помогите разобраться.»

**Выход:**
- Категория: `support`
- Sentiment: `negative`, Urgency: `high`
- Final answer: пронумерованные шаги (очистить кэш, проверить обновления, переустановить, отправить логи)
- Self-check: `ok`

**Вход:** «С меня списали деньги дважды за один и тот же заказ, требую немедленного возврата!»

**Выход:**
- Категория: `complaint`
- Sentiment: `negative`, Urgency: `high`
- Final answer: извиняющийся, эмпатичный ответ с обещанием возврата
- Self-check: `ok`

**Вход:** «Сколько стоит годовая подписка на профессиональный тариф и какие в неё входят функции?»

**Выход:**
- Категория: `sales`
- Sentiment: `neutral`, Urgency: `low`
- Final answer: короткий «продающий» ответ с приглашением на демо
- Self-check: `needs_review` (в ответе нет конкретной цены и списка функций)

## Результаты тестового прогона (10 текстов)

| Тип текста | Категория определилась верно | Self-check |
|---|---|---|
| support (2 текста) | 2 из 2 | ok / ok |
| feedback (2 текста) | 2 из 2 | ok / ok |
| complaint (2 текста) | 2 из 2 | ok / ok |
| sales (2 текста) | 2 из 2 | needs_review / needs_review |
| general_question (2 текста) | 2 из 2 | needs_review / ok |

Итого: все 10 текстов обработаны без ошибок шагов, все 5 категорий
определены верно, самопроверка пометила 3 ответа из 10 как
`needs_review`.

Routing работает заметно: ответ на `complaint` извиняющийся и длинный,
на `feedback` короткий и тёплый, на `support` в виде нумерованных шагов,
на `sales` — «продающий» с призывом к действию.

## Результаты Дня 4: классификация и routing

Двухшаговый пайплайн (классификация → генерация ответа с routing),
запуск `python day4_run.py`, результат в `output/day4_results.json`.
Все 10 текстов обработаны без ошибок, все категории определены верно
(по 2 текста на каждую из 5 категорий).

Routing заметно меняет стиль ответа:

- **complaint** — длинные извиняющиеся ответы с обещанием решения или компенсации («приносим наши самые глубочайшие извинения…», 369–612 символов).
- **sales** — короткие «продающие» ответы с призывом к действию («хотите, я вышлю детальную спецификацию или помогу с оформлением подписки?»).
- **feedback** — тёплые и короткие ответы с благодарностью (124–134 символа).
- **support** — ответ пронумерованными шагами.

Сравнение `complaint` и `sales` показывает требуемую разницу: первый
извиняющийся, второй «продающий».

Наблюдение: на Дне 4 нет самопроверки, поэтому модель свободно придумывает
факты. В ответе на вопрос о цене она назвала тариф «99 ₽ в месяц при оплате
за год» и перечислила функции, хотя в запросе таких данных нет. На вопрос
о скидках для команды ответила, что «действует привилегированный тариф
с существенной экономией». Это одна из причин, почему на Дне 5 добавлен
шаг `self_check`.

## Надёжность и тесты (День 6)

Три проблемных сценария проверены вручную, во всех пайплайн не упал
с трейсбеком, а обработал ситуацию.

### Сценарий 1 — слишком длинный ответ

Временно поставила `Field(max_length=50)` для `final_answer`.

- Попытка 1: модель вернула ответ длиннее лимита (795 символов), сработал `ValidationError`, в лог попало `ошибка валидации, повторяем с деталями ошибки...`.
- Текст ошибки Pydantic был добавлен в промпт повторной попытки.
- Попытка 2: модель уложилась в лимит, шаг прошёл успешно.

Вывод: fallback с подсказкой работает. Но короткий ответ получился
бессмысленным («1. Удалить кэш. 2. Обновить. 3. Демонтаж.»). Валидация
формата не гарантирует качество, и шаг `self_check` это поймал:
`consistent=False, verdict=needs_review` с описанием проблем. Самопроверка
нужна как отдельный слой. После теста лимит возвращён к `max_length=800`.

### Сценарий 2 — ошибка API (невалидный ключ)

Испортила последние символы `OPENAI_API_KEY`.

- Провайдер вернул `401 Invalid API Key`, `llm_client.py` поймал `openai.APIError` и вернул пустую строку.
- `_call_step` ушёл в retry: «пустой ответ, повторяем...».
- После 3 попыток шаг вернул `step_failed_after_retries`, пайплайн написал `Ошибка на этапе 'extract_meaning'` и перешёл к следующему тексту.

Замечание: повторять запросы при `401` бессмысленно, неверный ключ сам
не исправится. Возможное улучшение: сразу прекращать работу при
`AuthenticationError`. Ключ после теста восстановлен.

### Сценарий 3 — невалидный JSON

Проверка напрямую в консоли Python:

```python
>>> from utils import parse_model_json
>>> parse_model_json("это не json вообще")
json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)
```

Это то же исключение, которое ловит `_call_step`, после чего повторяет
запрос с напоминанием вернуть только валидный JSON.

## Эксперименты первых дней (Дни 1–3)

Подробные выводы — в `NOTES.md`. Файлы с результатами лежат в `output/`.

- **День 1** (`results.json`): на первых прогонах без валидации 2 из 3 ответов оказались `invalid_json`. Это показало, что ответ модели нельзя использовать как есть.
- **День 2** (`comparison.json`): сравнение трёх вариантов system prompt (`v1_minimal`, `v2_strict`, `v3_few_shot`) на одних и тех же текстах. Минимальный промпт дал непредсказуемую структуру JSON, строгий дал нужные поля, few-shot иногда переключал язык ответа на английский.
- **День 3** (`day3_results.json`): Pydantic-схема из 5 полей. 2 из 4 текстов не прошли валидацию: модель вернула `sentiment: "нейтрально"` вместо разрешённого `"neutral"`. Ошибки были пойманы и залогированы вместо падения программы.
